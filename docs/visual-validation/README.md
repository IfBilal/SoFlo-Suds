# Concept UI validation — 22 October 2026

The [Developer Handbook](../SoFlo%20Suds%20-%20Developer%20Handbook.pdf) decides features and flow. The client's saved [concept HTML](../soflo.html) decides the visual language where those features overlap. This review compares the rendered HTML and the Expo web preview at 390 px, then checks the app at 350 px and 320 px. The UI mockup PDF remains a separate workstream.

## Evidence and method

- The original eight long concept captures are in [`docs/concept`](../concept/). A fresh local Chrome run captured [12 in-scope concept routes at 390 px and 350 px](concept-live/) plus service detail, booking location/review, and a second garage vehicle. The app captures are in [`390`](390/) and [`350`](350/). They use marked fixture data through a Playwright API intercept; no customer, booking, payment, or Urable record was created to make the screenshots.
- From the repository root, start Expo web on port 8082 and run `npm run visual:capture`. Start `python3 -m http.server 8099 --directory docs` and run `npm run visual:concept` for the HTML reference. With the admin Vite server on port 5173, run `npm run visual:admin`. These scripts require Google Chrome at `/usr/bin/google-chrome` (or `CHROME_PATH`) and the mobile `.env` API URL set to `http://localhost:3000`. The app capture writes [`results.json`](results.json).
- The repeatable run checked 47 rendered cases: 19 signed-in routes at 390 px, four key routes at 350 px, 19 signed-in routes at 320 px, and five signed-out routes at 390 px. Each had a response, visible content, no document-level horizontal overflow, and no browser console/page error. Additional browser checks open service detail, follow Garage → Services → Booking with the selected vehicle, reach the web Urable handoff, switch to completed bookings, load the profile form, search an unmatched shop product, toggle a notification preference, render empty booking/vehicle states, and drag the gallery divider.
- The 11 handbook admin sections were captured at 1365 px and 390 px with fixture API responses, along with the Gallery add form: [admin captures](admin/). All 22 section views had no document overflow or browser errors. Forms and tables still need real-data and mutation checks.

## Open visual gates

1. Compare Android and iOS device screenshots with these 390 px references, especially fonts, status bar, safe areas, keyboard and the Urable WebView. Browser previews do not establish native parity.
2. Run the same comparison with real Urable services, a real booking, gallery images and approved product photos. Fixture data proves layout, not live content quality.
3. Visually verify the slider on touch devices, booking success/failure states, and admin upload/save/error states.
4. Apply the separate UI mockup PDF when it arrives, while keeping handbook scope final.

The observed visual foundation is close to the concept on the compared screens. The open gates above prevent an honest claim of full pixel parity or a release-ready UI.
