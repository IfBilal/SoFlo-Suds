## What was asked
Move the backend from Fastify (`apps/api`) to Supabase Auth, RLS, Edge Functions, Storage and Cron, keeping the handbook's features, the Urable integration and the concept-based UI, in small tested commits with docs kept current. Originally: do not cut over the live project, migrate real users or remove Fastify until Ali approves. Ali then approved the stack change (relayed verbally; written confirmation still pending) and the owner told me to proceed end to end on the live project, which was empty. `apps/api` is still in the repo, deliberately.

## What was done
**Database (`supabase/migrations/`, 4 files, applied to the live project):** initial schema; Auth identity mapping (`users.auth_user_id`, `admins.auth_user_id`) with default-deny RLS and column-limited grants; business functions in the `soflo_private` schema (profile completion, account delete, reward redemption, job recording with points and referral rules, sync lease); push ticket table.

**Edge Functions (`supabase/functions/`, deployed):**
- `soflo-api`: path-preserving port of the Fastify routes, same `{error:{code,message}}` contract, server-side token verification, ownership checks in code.
- `cron-worker`: leased, bounded Urable job sync, day-before reminders, Expo push receipts. Secret-header protected.
- `health`.
- Shared code in `_shared/` (Urable client, session, push, sync, errors).

**Cron:** pg_cron job `soflo-worker` every 5 minutes calls `cron-worker` through pg_net; the project URL and cron secret are in Vault. It replaces the old `sync:once`; never run both.

**Apps:**
- Mobile (`apps/mobile`): supabase-js with PKCE and a chunked SecureStore adapter; signup, verify-email and reset-by-deep-link (`soflosuds://reset`) flows; profile completion on first sign-in.
- Admin (`apps/admin`): Supabase sign-in, per-call session token.

**Ops scripts (`scripts/supabase/`):** `bootstrap-admin.mjs` (used), `migrate-legacy-users.mjs` (dry-run by default, never run, no legacy users exist).

**Tests:** `npm run test:db` (51, PGlite migration replay and RLS matrix), `npm run test:functions` (11 tests, 42 steps, real handlers on real migrations), `npm run check:functions`; typecheck and builds pass for api, mobile and admin.

**Live project setup (done through the Supabase Management API and MCP):** 4 migrations applied, pg_net/pg_cron enabled, secrets `URABLE_API_KEY`, `CRON_SECRET` and `ADMIN_ORIGINS` set, functions deployed, Auth site URL and redirect allow-list set, Brevo SMTP configured, email confirmation on, Cron scheduled. Security advisors show nothing critical. Live smoke test passed 18/18 (sign-in, profile completion and idempotency, own-row RLS, protected columns, admin separation, deactivated admin blocked, account deletion), and its test data was cleaned up.

**Admin site:** deployed to Vercel at https://soflo-suds-admin.vercel.app as a prebuilt static site (source builds fail on Vercel because of the monorepo install). Recipe: build `apps/admin`, copy `dist` into `apps/admin/.vercel/output/static`, add `config.json` with an SPA fallback, then `vercel deploy --prebuilt --prod`. CORS from that origin is verified. The owner admin account (muhammadbilaltahir06@gmail.com) exists and `/admin/me` returns 200 through the live API.

**Android build:** EAS project `@bilal06/soflo-suds` (id `4d9d4147-a1ef-4083-a3d0-14a12a63f09f`); `apps/mobile/eas.json` with `preview` (APK) and `production` (AAB); Android package `com.soflosuds.app`; keystore generated by EAS. Preview build `8fbdfd30-1777-4262-a28a-97809f5dd2b9` was started; check it with `npx eas-cli build:view 8fbdfd30-1777-4262-a28a-97809f5dd2b9`.

## Working rules and gotchas
- Never put the service-role key, the Supabase access token, the cron secret or the admin password in the repo or in chat. They live in the owner's shell and in local ignored `.env` files; the owner chose to keep the current service-role key.
- Commits are GPG-signed and the passphrase prompt can time out; retry rather than disabling signing.
- The Claude Code permission classifier blocks production-affecting commands until the owner approves them; do not work around a denial.
- There is no Docker here; database tests run on PGlite and function tests on Deno (`deno@2.9.6`) with a PGlite socket server.
- Keep `main` untouched.
